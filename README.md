# 特朗普交易雷達 / Trump Trade Radar

**線上版（每日自動更新）：<https://nik5011.github.io/trump-trade-radar/>**

手機可直接開啟，或在 Safari／Chrome 選「加入主畫面」當成 App 使用。
線上版是每日快照（每天台北時間 07:30 更新）；要即時同步請在本機執行 `node server.mjs`。

用美國總統特朗普的**申報股票交易**做訊號評分、投資組合建議與事件式回測的本機 Web App。

```bash
node server.mjs            # 開啟 http://localhost:8787
node server.mjs --port 9000
```

零外部依賴：不需要 `npm install`，只要有 Node 18+（本機測試於 Node 24）。

```bash
node --run test            # 執行測試（60 項）
node --run check-sources   # 探測各資料來源在你網路環境是否可連線
node --run oge:list        # 列出特朗普本人的 OGE 申報紀錄
node --run oge:download    # 下載 278-T PDF 正本到 data/oge/
```

## 一、最重要的前提：申報資料沒有真正的「即時」

這不是技術問題，是法規問題。美國總統依《政府倫理法》以 **OGE Form 278-T** 申報股票交易：

| 階段 | 實際情況 |
| --- | --- |
| 成交 → 申報 | 法定期限 **30 天內**；實際常見 1～3 週 |
| 申報 → 上網公開 | 數個工作天（OGE 作業） |
| **合計延遲** | **約 1～6 週**（本 App 會在每個訊號標示實際天數） |
| 揭露內容 | 只有**金額區間**與**成交日**，沒有精確股數與價格 |

因此「即時跟單特朗普買股」在物理上不可行。本 App 的做法是把能即時的部分做到最好：

### 真正能做即時的四條線（皆已實測可用）

| 來源 | 提供什麼 | 延遲 | 是否需金鑰 |
| --- | --- | --- | --- |
| **OGE 官方 API** | 特朗普每一筆 278-T 申報與 PDF 連結 | 申報上網即抓到（變動偵測） | 否 |
| **Yahoo Finance Chart API** | 真實市價（日線） | 盤中約 15 分鐘 | 否 |
| **Google News RSS** | 即時新聞快訊 | 發布後數分鐘 | 否 |
| **Federal Register / USAspending** | 政策、關稅、政府採購 | 公布即取得 | 否 |

`node --run check-sources` 會實測這些來源在你網路環境的可用性。

### 資料規模與價格分析池

真實申報資料有上千檔標的。為了不讓外部價格查詢與前端傳輸失控，App 只對
**申報金額最大的前 120 檔**抓真實價格（實測涵蓋約 75% 的申報金額），
其餘標的的動能分數以中性值處理，個股頁也會標示「此標的未在價格分析池內」。
這個上限定義在 `engine.mjs` 的 `PRICE_UNIVERSE_LIMIT`。

## 二、真實交易資料怎麼進來

App 內建兩種資料：**示範資料集**（41 筆模擬申報，僅供離線展示）與
**真實資料集**（一鍵載入，4,000+ 筆實際申報交易）。要載入真實資料，有四條路徑：

### 路徑 0：一鍵載入真實資料（最快）

在「資料管理 → 載入真實申報資料」按一下，或呼叫 API：

```bash
curl -X POST http://localhost:8787/api/import/external \
  -H 'Content-Type: application/json' -d '{"mode":"replace"}'
```

會從 GitHub 下載第三方已解析的 OGE 278-T 資料集並轉成 App 格式：

| 項目 | 內容 |
| --- | --- |
| 來源 | 原始檔為 OGE Form 278-T（2026-05-08 申報、2026-05-14 公開） |
| 範圍 | 2026-01-06 ～ 2026-03-30 |
| 筆數 | **3,642 筆交易 / 1,025 檔標的 / 14 個產業**（全部對應到股票代號） |
| 第三方倉庫 | `HerringtonDarkholme/trump-portfolio-tracker` |
| 注意 | 這是**第三方解析結果**，不是 OGE 官方結構化資料；每筆的來源都會標在交易明細頁 |

同一頁也會列出 `data/` 底下所有可匯入的 CSV，包含你自己用官方 PDF 解析出來的結果，
按「匯入這個檔案」即可（本機已內含一份 `data/oge/transactions.csv`，644 筆）。

### 路徑 A：通用 JSON 端點（最省事，適合已有訂閱者）

在「即時情報 → 申報資料自動匯入」貼上任何回傳紀錄陣列的 JSON 端點
（Quiver Quantitative、Unusual Whales、Capitol Trades 鏡像，或你自己的爬蟲）：

```bash
curl -X POST http://localhost:8787/api/sync/disclosures \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://your-endpoint/trades","apiKey":"YOUR_KEY","mode":"replace"}'
```

系統會自動在回應中找出紀錄陣列並對應欄位（ticker／日期／金額／買賣別），
不需要事先約定格式。

### 路徑 B：手動匯入 CSV / JSON

在「資料管理」頁貼上，或呼叫 API：

```csv
tradeDate,filedDate,ticker,company,side,amountMin,amountMax,owner,source
2026-08-18,2026-09-08,AMZN,Amazon.com Inc,BUY,1000001,5000000,本人,OGE 278-T
```

欄位名稱有容錯：`Transaction Date`／`Symbol`／`Type`／`Amount` 等常見寫法都能自動對應，
金額可寫 `$1,000,001 - $5,000,000`，日期可寫 `8/18/2026`。

### 路徑 C：從 OGE 正本自己建管線（已可運作）

```bash
node --run oge:list        # 已可用：列出真實申報清單（24 筆，其中 18 筆 278-T）
node --run oge:download    # 已可用：下載 PDF 正本到 data/oge/
python scripts/check-pdf-text.py           # 檢查哪些 PDF 有文字層
python scripts/extract-oge-transactions.py  # 解析成 CSV（預設寫到 data/oge/transactions.csv）
```

已驗證的官方端點（OGE 官網搜尋頁背後就是它）：

```
https://extapps2.oge.gov/201/Presiden.nsf/API.xsp/v2/rest
```

實測要點（都已寫進 `providers.mjs`）：

- 這是 DataTables 伺服器端介面，**必須帶 `start` / `length`**，否則一次回 1.6 萬筆（約 7MB）。
- **全域 `search[value]` 會被忽略**，必須用欄位搜尋 `columns[3][search][value]=Trump, Donald J`。
- 姓名格式是「姓, 名」（`Trump, Donald J`）。
- 用 GET；POST 會回 400。

實測結果：18 份 278-T 申報中，**17 份有文字層**（多為掃描後 OCR 的檔案，文字有雜訊但可解析），
只有最新一份（2026-08-12 申報）是純掃描影像需要 OCR。解析器的作法是：

1. 用「日期後面接著 Yes/No 欄位」定位交易列，避開描述中的到期日。
2. 金額先移除空白再切分（OCR 會把千分位逗號變成空白：「$250 001」= $250,001）。
3. 買賣別用模糊比對分類（OCR 常把 purchase 認成 lourchaso／ourdulso 等）。
4. 以第三方整理的 OGE 描述別名表把「公司描述」解析成股票代號。

目前從最新可解析的申報（2026-06-25 申報、44 頁）解析出 786 列，其中 644 列成功對應股票。
要注意 2025 年的申報大多是**市政債與公司債**（沒有股票代號），所以股票交易主要集中在 2026 年。

若你要處理那份純掃描檔，需要額外安裝 OCR：

```bash
pip install pdfplumber pytesseract      # 另需安裝 Tesseract OCR 引擎
python scripts/inspect-oge-pdf.py data/oge/<檔名>.pdf --pages 3 --tables
```

若你的環境沒有 OCR，實務上的最佳組合是：**路徑 0 取得大批交易明細 + OGE API 做權威核對**。

## 二之一、放到免費空間，用手機隨時看

這個 App 預設是「本機伺服器」，但它可以**匯出成純靜態網站**，放到任何免費空間
（GitHub Pages、Cloudflare Pages、Netlify…），手機開瀏覽器就能看。

```bash
node server.mjs                 # 先讓本機伺服器跑著（資料來源）
node scripts/build-static.mjs   # 匯出到 dist/
node scripts/serve-static.mjs   # 本機預覽 http://localhost:8080
```

`dist/` 裡面只有靜態檔（HTML / JS / CSS / JSON，約 6 MB），沒有任何後端需求：

| 檔案 | 說明 |
| --- | --- |
| `index.html` | 注入 `window.__TTR_STATIC__`，把資料來源指向 `data/*.json` |
| `engine.mjs` → `engine.js` | 分析引擎；改名是因為部分免費空間對 `.mjs` 會回錯的 MIME 類型，瀏覽器會拒載 |
| `data/*.json` | 15 個端點的快照，含 4,286 筆申報交易、120 檔真實價格、政策文件、內部人交易 |
| `app.js?v=<hash>` | 加上版本雜湊，避免免費空間的快取讓你看到舊版 |

**靜態版的限制**：資料新鮮度＝建置時間，而且所有「同步／匯入」按鈕會自動隱藏，
頁面上方會顯示目前是快照版本與資料時間。完整功能請在本機跑 `node server.mjs`。

### 自動每天更新（GitHub Pages，完全免費）

專案已附 `.github/workflows/deploy-pages.yml`：

1. 把整個專案 push 到 GitHub。
2. 到 **Settings → Pages**，Source 選 **GitHub Actions**。
3. 工作流程每天 UTC 23:30（台北 07:30）自動執行：載入真實申報資料 → 抓價格、政策、
   新聞、合約、OGE 申報清單、事件日曆、市場體制、內部人交易 → 產生靜態版 → 部署。

4. 完成後手機打開 `https://<你的帳號>.github.io/<專案名>/` 即可。

`.gitignore` 已排除 `data/positions.json`（你的持股）與申報 PDF 正本，
個人部位不會被上傳到公開空間。

其他免費空間：`dist/` 是純靜態檔，拖到 Cloudflare Pages 或 Netlify 也可以；
若網站掛在子目錄（例如 `https://example.com/stock/`），用
`node scripts/build-static.mjs --base /stock/` 重新產生即可。

## 三、分析引擎

### 內部人交易（SEC Form 4）：延遲最短的訊號

Form 4 必須在交易後 **2 個營業日**內申報，幾乎沒有延遲，而且是「本人下單」的直接證據——
這是它比總統申報（延遲 1～6 週）有用得多的原因。資料來自 SEC EDGAR，免費、無需金鑰。

抓取流程：

```
ticker → CIK        https://www.sec.gov/files/company_tickers.json
公司申報索引        https://data.sec.gov/submissions/CIK##########.json
交易明細 XML        https://www.sec.gov/Archives/edgar/data/{cik}/{accession}/xxx.xml
```

SEC 的公平使用政策要求帶可識別的 User-Agent 且每秒不超過 10 次請求，
程式中用全域節流控制在 8 次/秒（可用環境變數 `TTR_SEC_UA` 換成你自己的聯絡資訊）。

**只把「買進」算進分數**（集群程度 45% ＋ 金額 35% ＋ 職位 20%）：
賣出大多來自薪酬流程（行使選擇權後賣出、稅務扣繳）或既定的 10b5-1 計畫，預測力很弱；
授予（A）、稅務（F）、贈與（G）則完全不是訊號。

**實測結果（掃描申報金額前 36 大標的、近 120 天、392 筆交易）**：

| 標的 | 分數 | 買進 | 買進金額 | 集群 | 備註 |
| --- | --- | --- | --- | --- | --- |
| **UBER** | 75.5 | 3 筆 | **$15.31M** | 2 人 | 執行長 Khosrowshahi 9/10 買 $10.01M、Macdonald 9/4 買 $5.31M |
| MO | 30.5 | 1 筆 | $0.10M | 1 人 | 董事買進 |
| ETN | 30.3 | 2 筆 | $0.09M | 1 人 | 董事買進 |

同一段期間，內部人賣出金額是 $430M 等級——**內部人買進是稀有事件**，
所以看到集群買進時的資訊量特別高。頁面也做了交叉比對：UBER 同時出現在
「內部人集群買進」與「總統申報淨買入 +$2.45M」兩份清單上。

過程中修掉兩個 bug：① 掃描取的是價格池的**字母序前 36 名**而不是申報金額前 36 名
（導致只掃到 A 開頭的公司），已改用 `rankedTickers`；② 買進明細被截斷，
因為程式先取前 200 筆才過濾交易代碼，導致較早發生的買進被大量賣出洗掉，改成先過濾再排序取樣。
另外 SEC 的申報索引也會列出「公司只是申報人（例如 10% 股東）」的 Form 4，
所以要驗證 XML 內的 `issuerCik` 等於查詢的 CIK，否則會混進別家公司的交易。

### 我的部位：把「我的帳」跟所有訊號交叉比對

匯入只需要 `ticker,shares,avgCost`（成本選填）：

```csv
ticker,shares,avgCost
NVDA,120,180.50
AMZN,80,230.00
```

貼進「我的部位」頁或用 API 匯入後，會算出：

1. **部位明細** — 市值、權重、未實現損益、持股市數佔日成交量比例、跳空風險。
2. **風險彙總** — 產業集中度、政策曝險分布（受惠／受損／中性）、
   組合單日 95% 分位風險（各部位加總，未考慮相關性，因此是低估值）。
3. **訊號交叉比對** — 每一檔同時顯示政策方向、AI 下跌機率、最近的財報日。
4. **警示** — 單一部位過重、產業過度集中、持倉佔日量過高（出場會滑價）、
   財報將至、位於下跌機率前段、政策逆風。

部位資料只寫在 `data/positions.json`（你自己的電腦），不會上傳。
沒有成本欄位也能用，只是不算損益。

### 市場體制：先看環境，再看訊號

單一訊號脫離環境幾乎沒有意義。這一頁用 **15 個跨資產維度**算出「風險偏好 ↔ 風險趨避」的綜合分數：

| 類別 | 維度 |
| --- | --- |
| 股市 | S&P 500 距 200 日均線、市場寬度（RSP/SPY）、小型股偏好（IWM/SPY） |
| 波動 | VIX 水位、VIX 20 日變化、波動風險溢酬（VIX ÷ SPY 已實現波動） |
| 利率 | 10 年期殖利率水位、20 日變化、殖利率曲線（10Y − 3M） |
| 信用與匯率 | 信用風險偏好（HYG/LQD）、美元指數 20 日變化 |
| 商品與區域 | 銅金比、油價、科技領導（SMH/SPY）、新興市場（EEM/SPY） |

每個維度算「相對自己歷史的水位」（0～100），並用**擴張視窗百分位**（只用當日之前的資料）
避免前視偏誤——測試檔裡有一項專門驗證「加入未來資料不會改變歷史分數」。
資料全部來自 Yahoo Chart API，免費且無需金鑰。

**目前的讀數（2026-09-11，綜合 38/100「中性偏防禦」）**：

| 最強 | 最弱 |
| --- | --- |
| 殖利率曲線 99（10Y−3M = +1.06，無倒掛） | 利率水準 0（10 年債 4.97%，近兩年最高區間） |
| 新興市場 81 | 油價 5（20 日 +23%，通膨壓力） |
| 波動水準 75（VIX 15.8 偏低） | 小型股偏好 11 |

**體制別訊號表現**：同一組訊號在不同體制下的命中率差距（相對同體制基準，20 日）：

| 訊號 | 風險偏好 | 中性 | 風險趨避 |
| --- | --- | --- | --- |
| 距 52 週高點 < 3%（強勢股） | **+8.8pp** | +2.9pp | **−26.8pp**（n=29） |
| 60 日動能 < −15%（跌深） | −5.6pp | **+7.2pp** | −8.6pp |
| 近 30 天內有買入申報 | +2.7pp | +8.3pp | +13.7pp（n=4） |

結論很直接：**強勢股策略只在風險偏好時有效，跌深反彈只在中性體制有效**。
樣本期間大多是中性到風險偏好，所以風險趨避那一欄的樣本數要看清楚再用。

### 事件時鐘：什麼時候該進出

交易決策不只需要「買什麼」，更需要「什麼時候」。這個頁面把未來 N 天的事件排成一條時間軸：

| 事件類型 | 來源 | 為什麼重要 |
| --- | --- | --- |
| **政策生效日** | Federal Register API 的 `effective_on` | 供應鏈、成本結構與補貼會在這天重新定價 |
| **評論截止日** | Federal Register 的 `comments_close_on` | 規則尚未定案，之後可能翻盤 |
| **財報日** | Nasdaq 財報日曆（公開端點） | 盤後財報是跳空風險最高的時點，部位大小應該不同 |
| **合約公告** | USAspending | 政府訂單對國防、工業、IT 類股是實質基本面 |

只保留我們追蹤的標的，並用標題／摘要相關性過濾掉無關的例行公告
（實測 45 天內抓到的政策事件從 119 筆降到 17 筆真正相關的）。

### 執行與計分：吃得下多少、訊號何時失效

**容量與流動性**：每檔標的算 20 日均額（ADV）、`申報金額 ÷ 日成交量`（要花幾天的量才吃得完）、
單筆建議上限（以單日不超過 10% ADV 估算）、以及單日波動的第 95 百分位當跳空風險。
實測結果：KRUS、COMT 這類小型標的，他的申報金額相當於半天的成交量；
但多數大型股只佔日量的 0.1～0.5%，容量完全不是問題。

**訊號衰減曲線**：同一個訊號在 1／5／10／20／40／60 日的命中率相對全體平均的差距（pp）。
這一欄揭露了很重要的東西：

| 訊號 | 1 日 | 20 日 | 60 日 |
| --- | --- | --- | --- |
| 近 30 天內有買入申報 | **−17.2pp** | +5.6pp | **+13.0pp** |
| 近 90 天買入 ≥ 3 筆 | **−19.9pp** | +6.8pp | +10.3pp |
| 60 日動能 > +15% | −2.4pp | −0.5pp | −5.5pp |

也就是說：**申報公布後的第一天反而偏跌（短線反轉），優勢要到 20～60 日才出現**。
如果你在申報公開當天跟單，歷史上是站在錯的一邊。這正是「衰減曲線」要回答的問題。

**資訊係數（IC）**：特徵與未來報酬的秩相關。|IC| > 0.05 才算有微弱預測價值，
0.02～0.03 基本在雜訊範圍。目前最高的幾個是申報買入筆數與新穎度（60 日約 +0.07～0.09，
1 日則顯著為負），政策曝險的 IC 約 −0.04（方向與直覺相反，值得警惕）。

### AI 機率模型：可檢驗的漲跌機率，不是預言機

「AI 機率」頁用歷史資料訓練一個羅吉斯迴歸，估計「未來 N 個交易日上漲的機率」。
重點是**整個流程可被檢驗，而且結果照實呈現**：

| 項目 | 做法 |
| --- | --- |
| 特徵（11 個） | 20/60 日動能、相對大盤強度、波動度、距 52 週高點、成交量變化、申報淨買入、申報買入筆數、申報新穎度、政策曝險、政策事件密度 |
| 防止前視偏誤 | 申報特徵一律用 **filedDate（申報日）**，不是成交日；價格只用當日與之前的資料。`test/providers.test.mjs` 有專門測試 |
| 資料切分 | 前 55% 訓練 → 中 15% 做機率校準 → 後 30% 才是樣本外測試 |
| 機率校準 | 羅吉斯迴歸原始輸出常常過度自信（例如毫無訊號卻說 98%），用驗證集把分數映射成實際命中率 |
| 誠實指標 | 同時顯示樣本外準確率、**基準率（一律猜多數類）**、AUC、校正前後的預測誤差 |

**目前的實際結果（2026-09 資料，未來 20 個交易日）**：

```
樣本 5,310 筆（118 檔標的）        訓練 2,921 筆 / 樣本外測試 1,593 筆
樣本外準確率 57.9%  ←  基準率也是 57.9%（測試期間是多頭市場）
AUC 0.516           ←  0.5 代表與亂猜無異
```

模型自己給出的判定是「**沒有可證實的預測優勢**」。頁面上的比較表也測試了 4 種特徵組合
（全部特徵／只用申報訊號／申報＋動能／只用價格與量），AUC 全部落在 0.49～0.52，差異屬於雜訊。
這些都不會被藏起來——如果哪天真的有優勢，同一張表也會照實顯示。

**更有用的部分是條件機率表**：不做黑箱，直接看「符合某條件時，歷史上漲機率是多少」，
並列出目前符合條件的標的。以未來 20 日、全樣本 5,310 筆觀察值為例：

| 條件 | 樣本數 | 上漲機率 | 相對全體 |
| --- | --- | --- | --- |
| 近 30 天內有買入申報 | 772 | 59.6% | **+6.7pp** |
| 近 90 天買入 ≥ 3 筆 | 1,265 | 59.3% | **+6.4pp** |
| 政策對照為受損型 | 540 | 57.4% | +4.5pp |
| 近 90 天申報淨買入 > $1M | 431 | 52.0% | −0.9pp |
| 60 日動能 > +15% | 878 | 47.8% | **−5.1pp** |

也就是說：**「有申報買入」比「股價已經漲很多」更有參考價值**，而大額申報本身反而沒有優勢。
這些是歷史描述統計（樣本期間偏多頭），不是未來的保證。

### 政策雷達：政策主題 × 持股的交集

「政策雷達」頁把**特朗普政府提出的政策**與**他申報的實際買賣**接在一起：

| 步驟 | 做法 | 可驗證性 |
| --- | --- | --- |
| 1. 抓政策文件 | 12 個主題各自用關鍵字向 Federal Register 官方 API 查詢 | 官方 API，每份文件都可點開原文 |
| 2. 時間涵蓋 | 依季切窗抽樣，涵蓋 2025-05～至今（不是只抓最新幾筆） | 每份文件都標示發布日 |
| 3. 相關性過濾 | 只保留「總統文件／法規／擬議法規」，且關鍵字須命中**標題**或夠特定的**摘要**字詞 | 實測 569 份抓取中保留 73 份，濾掉例行公告與不相關文件 |
| 4. 對照個股 | 每個主題列出政策方向上相對受惠／受損的標的（`policy-map.mjs`，可自行修改） | 對照表完全公開可編輯 |
| 5. 計算交集 | 標的交易與政策文件日期相差 ±N 天即算一筆交集（N 可調 14/30/60/90） | 交集只代表時間接近 |

12 個主題：關稅與貿易救濟、半導體與出口管制、能源開採與油氣、國防採購與軍費、
移民執法與邊境、加密貨幣與數位資產、藥價與醫療保險、AI 與電力基礎建設、
聯邦 IT 與政府效率、金融監理鬆綁、汽車與電動車政策、媒體與電信監理。

**圖表**：

1. **政策曝險 × 申報淨買賣散佈圖** — 橫軸負值＝受損型曝險、正值＝受惠型；縱軸為淨買賣；
   圓圈大小＝申報金額。「政策受惠卻淨賣出」或「政策受損卻淨買入」是最值得細看的象限。
2. **產業資金熱力圖（treemap）** — 面積＝申報金額、綠＝淨買、紅＝淨賣。
3. **政策事件 × 交易時間軸** — 上緣黃點是政策文件發布日、下方柱子是該週淨買賣、
   黃色陰影是交集時間窗，可直接看出政策與交易在時間上的相對位置。
4. **交集明細表** — 每筆配對都列出政策文件標題、連結、日期、交易日期與差距天數。

> ⚠️ 交易與政策事件在時間上接近，**不代表任何因果關係或違法情事**。
> 政策對照方向是本工具的啟發式設定，不是投資建議。

訊號分數（0–100）由五個分項加權而成，權重可在「訊號排行」頁即時調整：

| 分項 | 預設權重 | 說明 |
| --- | --- | --- |
| 部位規模 | 28% | 近 365 天申報買入金額（對數壓縮） |
| 訊號新穎度 | 22% | 距最近買入的天數，45 天半衰期指數衰減 |
| 加碼節奏 | 20% | 近 180 天買入次數，並對 30 天內密集加碼加成 |
| 價格動能 | 18% | 60 日與 120 日報酬 tanh 標準化 |
| 申報熱度 | 12% | 近 90 天買入筆數與跨帳戶重複度 |

另外套用**淨賣出懲罰**：同期有減碼時按比重下調分數。

**投資組合**：依分數加權（γ 次方）配置，套用單一持股上限、單一產業上限與最低現金比重；
若達門檻的標的不足，超額資金留在現金並在說明中告知原因。

**回測**：事件式模擬，**以「申報日」而非「成交日」為訊號日**（避免使用當時尚未公開的資訊），
可設定進場延遲、持有天數、單筆部位、同時持倉上限與手續費，並與等權大盤比較。
